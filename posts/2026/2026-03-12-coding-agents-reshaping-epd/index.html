Coding Agents 正在重塑工程、产品与设计的分工逻辑

软件公司的工程（Engineering）、产品（Product）与设计（Design）——EPD 三位一体——本质是造出能用的软件。分工虽细，最终交付物只是一行行代码。

但 Coding Agents 让代码突然变得极度廉价。

2026 年 3 月初，LangChain 创始人 Harrison Chase 在 X 发布长文，直言「PRDs 已死」，引发业内 69.5 万次阅读、近 4000 次收藏。他提出一个核心判断：当实现成本趋近于零，EPD 的瓶颈将从「写代码」转向「审代码」，三种角色将重新排布。

PRDs 已死：从文档驱动的瀑布流，到原型驱动的迭代流#

传统软件开发流程是一条清晰的瀑布：有人（通常是产品经理）想出一个点子 → 产品经理写 PRD（产品需求文档）→ 设计师按 PRD 画 Mock → 工程师把 Mock 变成代码。

这条路径 textbooks 般标准，但并非铁律。创业公司里这些步骤常常混在一起，最优秀的 Builder 往往能跨多个环节。但之所以还有这条「标准流程」，是因为写软件（以及画 Mock）需要大量时间和精力。于是产生了专业分工，也产生了跨分工沟通的需求——PRD 就是这个沟通的基石，一切从这里开始，再瀑布流到设计、工程。

Coding Agents 改变了这一切。

Chase 的观点很直接：Coding Agents 可以把一个点子直接变成能用的软件。当他说「PRDs 已死」，他指的是这种以写 PRD 为起点的传统软件开发方式已死。

但这不意味着描述产品需求的文本已死。

假设某人有个想法，然后快速生成了一个原型。这个原型怎么进生产环境？它需要 EPD 其他成员审查。审查过程中，一个书面文档总是有帮助的，甚至是必需的——当别人在看代码时，怎么知道某段代码是误写的还是有意的？这取决于意图。而意图需要被传达。

Chase 认为，传统的 PRD → Mock → Code 流程已死，但描述产品需求的文本非常活跃。这份配套文档应该在原型被交接审查之前就准备好。

未来的 PRD 会是什么样子？Chase 抛出一个有趣的问题：如果未来的 PRD 就是结构化的、版本化的 Prompt 呢？

瓶颈从实现转向审查：当任何人都能写代码，但不是所有人都能审代码#

任何人现在都能写代码，这意味着任何人都能做东西。但这不代表做出来的东西架构良好，不代表解决了正确的问题，也不代表好用。

工程、产品和设计应该成为这些维度的审查者和仲裁者。问题是生成的代码并不总是「好的」。EPD 的角色变成了审查并确保它是「好的」。「好的」可以意味着：

  • 从工程系统角度架构良好：是否以可扩展、高性能、稳健的方式编写？
  • 从产品角度思考充分：是否解决了用户痛点？
  • 设计精良：界面是否易用、直观？

由于创建某个初始版本代码的成本如此低廉，我们看到原型数量大幅增加。这些原型成为焦点，产品、工程和设计围着它们审查。

问题在于——生成代码太容易了。以前，写代码需要一段时间，作为审查者，任何时候桌面上只有那么多项目需要审查。但现在——任何人都能写代码。这意味着进行的项目数量在增加。我们在所有三个职能中看到的瓶颈都是审查——拿着原型并确保它们是「好的」。

一位硅谷工程师私下说：「以前我一周审 5 个 PR，现在一天能收到 20 个 Agent 生成的 PR。质量参差不齐，但拒绝的代价是打击同事的积极性。」

全才比以往更有价值，Coding Agents 成为必备技能#

Chase 所说的「全才」，是指对产品和设计都有良好感觉的人。这些人一直很有价值、很有影响力——但有了 Coding Agents，他们更加如此。

为什么？

沟通是一切中最难的部分。它拖慢进度。一个能同时做产品、设计和工程的人，会比一个三人团队更快，因为沟通开销更少。

以前，当实现是阻塞点时，这个全才仍然需要与他人沟通才能完成工作。现在他们可以直接与 Agents 沟通。这意味着他们仅凭自己就能比以往任何时候都更有影响力。

Coding Agents 让实现变得廉价，使用它们成为必需。

采用 Coding Agents 的人将能够自己做更多：

  • 采用 Coding Agents 的 PM 可以直接构建原型来验证想法，无需写 Spec 然后等待
  • 采用 Coding Agents 的设计师可以在代码中迭代，而不仅在 Figma 里
  • 采用 Coding Agents 的工程师可以将时间从实现转移到系统思考

采用 Coding Agents 是必需的，因为做到这一点并不难，而如果你不这样做，你会被这样做的人取代。

好 PM 更稀缺，坏 PM 更危险#

好的产品思维比以往更有价值——你能做出有用的东西。坏的产品思维比以往更有害。

如果某人有糟糕的产品想法，他们可以带着原型出现——但这个原型会是一个无用或构思拙劣的功能。这些原型现在需要更多的审查——来自工程、产品和设计。这消耗时间和资源。把这些原型投入生产也有更大的惯性（「它已经存在了！直接合并吧！」）。这有可能创造一个更差或臃肿的产品。

Chase 的警告并非空穴来风。

2025 年底，一家刚完成 B 轮融资的 AI 创业公司推行「全员 Agent 编程」，结果三个月内代码库膨胀 300%，核心功能反而出现 Regression。最终不得不用一个月时间专门「还债」——重构、删除无用代码、补测试。

「Agent 不会替你思考该做什么，它只是加速你的思考。」一位参与重构的工程师说。

系统思考成为区分技能，产品感成为全员必备#

在一个执行廉价的世界里，系统思考成为区分因素。

你应该专注于真正擅长系统思考，并对你的特定领域有清晰的心智模型：

  • 工程：对如何架构服务、API 和数据库有非常好的心智模型
  • 产品：对用户的真正需求（而非他们说的想要）有非常好的心智模型
  • 设计：对为什么某些东西看起来和感觉上是对的，有非常好的心智模型

系统思考一直很重要——那么什么改变了？实施成本大幅下降。这意味着实施某事比以往任何时候都容易——但这不代表它是好的。成为一个好的系统思考者让你能确保你 upfront 就在构建正确的东西。它也让你在事后审查他人的工作。两者都意味着，成为一个好的系统思考者的重要性增加了。

每个人都需要产品感。

Coding Agents 仍然需要有人 Prompt 它们。有人告诉它们做什么。如果你告诉它们构建错误的东西——你就是在为别人制造更多的 Slop 来审查。知道告诉 Agent 构建什么（「产品感」）是必需的，否则你会成为组织的拖累。这对工程、设计以及（显然的）产品都成立。

EPD 的大部分工作现在是审查原型。如果你有产品感，审查更容易，即使是审查设计/工程。如果你没有产品感，你需要一个超详细的产品文档 accompany 原型。如果你有产品感，你用最小的 Spec 就能理解功能的意图，加速沟通、审查和交付。

角色分化：你要么是 Builder，要么是 Reviewer#

Chase 看到 EPD 中出现两种不同的角色分化。

Builder：从想法到原型的创造者

这个群体有良好的产品思维，能够使用 Coding Agents，并有基础的设计直觉。在有 guardrails（测试套件、组件库）的情况下，他们可以把小功能从想法带到生产，并原型化更大功能的功能版本。

他们擅长快速验证，用代码说话。

Reviewer：从原型到生产的把关者

对于大型复杂功能，需要详细的 EPD 审查。这个门槛很高——你必须是你领域的杰出系统思考者。你还需要以快节奏工作——有很多东西要审查。

他们擅长系统判断，用标准把关。

如果你是工程师——你现在要么瞄准成为杰出的系统设计者，习惯审查架构并成为 Reviewer……要么尝试培养你的产品/设计技能成为 Builder。

如果你在产品或设计——你要么对产品/设计有极好的心智模型并主要 Review，要么跳入 Coding Agents 并提升你的 Coding 能力成为 Builder。

有趣的是，角色正在某种程度上融合。所有 EPD 都在 Builder-Reviewer 光谱的某个位置。工程师有更多时间，可以更多思考产品和设计。产品和设计可以创造代码。

每个人都认为自己的角色最受 Coding Agents 青睐——而他们是对的#

Chase 引用了一条 X 上的热门帖子，关于最受 Coding Agents 青睐的人：

那些对产品有一种直觉把握的人，知道它哪里是软肋，哪里是亮点，以及如何迭代它走向更锐利。

这种人的最稀有版本坐在文化与深度技术的交汇处。真正双语的人。他们知道什么是技术上可能的，也知道哪些文化潮流是真实的、哪些是短暂的。那种组合才是区分感觉 inevitable 的产品与感觉拼凑的产品的东西。

这条帖子半病毒式传播了。它传播的部分原因是每个读它的人都觉得是关于自己或自己的角色。Chase 看到产品人引用它，设计师，设计工程师，创始人……每个人都觉得它适用于自己和自己的角色。

而他们很可能都是对的。

Chase 发自内心地相信这个新世界里背景不那么重要了。他发自内心地相信这种原型的人可以来自产品、设计或工程。这不意味着每个人都会成为这种人——说起来容易做起来难。外面很少有真正的独角兽。

这是一个令人兴奋的建设时代。

一位在硅谷工作十年的华人工程师对《晚点》说：「Chase 的描述让我想起 2008 年 iPhone SDK 发布时的感觉——工具民主化了，但真正的壁垒从『会不会用』变成了『知不知道做什么』。」

说到底，Coding Agents 并没有消灭 EPD 的分工，而是把分界线从「写代码的人」和「不写代码的人」之间，挪到了「能审代码的人」和「只会写代码的人」之间。工具越强大，判断越值钱。
